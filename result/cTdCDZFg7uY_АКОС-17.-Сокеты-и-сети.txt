И что делать с этими портами, у которых номера меньше, чем 1024, как их можно использовать? Исторически вообще считалось, что серверный софт какой-то надежный, он может работать из-под рута. Затем в старых юних системах был еще отдельный демон, который принимал входящие соединения и перенаправлял их нужным серверам.
В современных системах такое обычно не используется, то есть каждый сервер с какой-то функциональностью он сам открывает нужный себе порт и вообще говоря, желательно, чтобы он запускался не из-под рута.
Представьте себе, что вы запускаете веб-сервер из-под рута, только для того, чтобы иметь возможность открыть 80-й порт. У вас происходит какой-то баг, например, запускается скриптик, мрф слэш, но это будет печально.
Поэтому нужно иметь какой-то механизм для запуска непривилегированными процессами, для открытия непривилегированными процессами портов с номерами меньше, чем 1024. Как это делается? Давайте запомним о том, что сокет у нас файловый дескриптор. Что можно делать с файловыми дескрипторами? Их можно наследовать в датчальных процессах.
Соответственно, если вы запустили какой-то дочерний процесс, то вся настройка, которая произойдет над сокетом, она будет влиять в том числе на тот файл дескриптора, который у него уже есть.
Поэтому операцию связывания bind какого-то сокета с некоторым именем, который требует прав рута, чтобы использовать порт с номером меньше, чем 1024, можно выполнять в дочернем процессе. Нужно как-то локально поднять привилегии дочернего процесса.
Как это делается? Команда su, которая требует пароль. Тут не системный вызов. set user id flag. Кто помнит, что это такое? Да, это некоторый атрибут файла, который предписывает, что применим к исполняемым файлам, указывает, что файл должен быть запущен из-под того пользователя, кому он принадлежит.
В частности, так реализованы sudo, su... Чем такие файлы плохи? Исполняемые тем, что они очень опасны. Любой пользователь может из-под рута запустить все, что угодно. Обычно, например, разработчики Linux дистрибутивов, ментейнеры пакетов вручную делают ревью такого кода, который компилируется с set user id flag.
Для того, чтобы сделать пакеты, в которых содержатся файлы с id flag, требуется ручная подпись, верификация, что действительно проверено, багов нет. То есть, как правило, это какие-то небольшие программы, которые выполняют маленькую, хорошо верифицированную функциональность.
И для того, чтобы не изобретать велосипед, в некоторых дистрибутивах типа Debian и Ubuntu есть уже готовые пакеты, которые занимаются ровно тем, что по некоторому access control list определенным приложениям разрешать использовать порт с номерами 1024, ровно для того, чтобы не дублировать функциональность, которая требует верификации.
В других дистрибутивах это нет, а в CentOS, например, это делается отдельным механизмом через seedcap. Но универсальный способ, он все-таки вот такой велосипед. Создать сокет в дочернем процессе по вести привилегии, связать, ну и сообщить родителю, что сокет уже связан.
